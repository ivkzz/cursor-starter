# AI Layer Bootstrap — оркестратор `.cursor/` и корневого `CURSOR.md`

**Принципы AI-слоя** — `@.cursor/PRINCIPLES.md` (читай перед началом). Этот файл — **только сценарий 8 шагов**, без повторения принципов.

Кратко: ты не «натягиваешь шаблон», а **проектируешь управляемую автономию**. Пользователь задаёт намерение (slash-команды, `@CURSOR.md`, короткий запрос); AI-слой классифицирует задачу, выбирает маршрут, принимает решения в рамках политик и уточняет у человека только при необходимости.

## Роль AI-слоя

| Слой | Назначение |
|------|------------|
| `CURSOR.md` | Карта маршрутизации (что → какая команда/skill, когда эскалировать). |
| `.cursor/rules/*.mdc` | Жёсткие политики (token economy, model routing, архитектура, стек, антипаттерны, secrets-guard, реестр скилов). Каждое правило — один фокус. |
| `.cursor/commands/*.md` | Контракты намерения: входы, шаги, лимиты, критерий «готово». |
| `.cursor/skills/` | Проектные многошаговые workflow (если возникает потребность). |
| Hooks | Активная часть: автопроверки в Cursor IDE и git (генерируются в шаге 4, не лежат в шаблоне). |

Итог: **пользователь говорит что → слой решает как** в пределах правил и таблиц.

## Инварианты

1. **Оркестратор-индекс** — только `CURSOR.md` в корне; таблицы и `@`-ссылки, без копий правил.
2. **Rules / Hooks / Skills** создаются через `/create-rule`, `/create-hook`, `/create-skill`. Проектные `.cursor/commands/*.md` — только **свои** сценарии (см. `@ai-layer-builder/spec-commands.md`), не дубли `create-*`.
3. **Merge, не выжигай**: дополняй существующее; полная перезапись `.cursor/`, `CURSOR.md`, `hooks.json` — только по явной просьбе пользователя.
4. После шага 0 не повторяй длинные политики — `@.cursor/rules/token-economy.mdc` и `@.cursor/PRINCIPLES.md`.
5. **Минимально достаточный набор** правил/команд/скилов под реальный репозиторий — без энциклопедий и дублей (P7).
6. **Нет готовых примеров**: анализируй проект, генерируй с нуля (P6).
7. После каждого крупного шага — краткий отчёт.

Структуру `CURSOR.md` бери из `@ai-layer-builder/spec-CURSOR.md`. Формат команд — `@ai-layer-builder/spec-commands.md`.

### Справка: глобальные скилы (только для человека; агент **не** устанавливает и **не сканирует диск**)

На машине разработчика могут быть установлены глобальные скилы Cursor (`~/.cursor/skills/`, `~/.cursor/skills-cursor/`, `~/.cursor/plugins/`). Cursor подхватывает их как slash-команды автоматически.

**Шаблон сознательно не сканирует диск.** На типичной машине — тысячи скилов; запись их всех в правило — диверсия против token-economy. Реестр работает по обратной модели: пользователь **сам** добавляет нужные скилы в `@.cursor/rules/project-skills-registry.mdc` (см. шаг 2.5). Установку выполняет **только человек** вне этого сценария; `npx`, установщики, сетевые команды — не запускать.

## Шаг 1.5. Живая Документация (Living Documentation) и Планирование

**А. Живая Документация (State/Memory)**
Архитектура должна включать ведение структурной "памяти" проекта — Живой Документации (например, `PROJECT_KNOWLEDGE.md` или папку `docs/`). 
- **Запрещено** вести лог (append-only) в стиле "я добавил файл X, я поправил баг Y". 
- **Обязательно** обновлять саму структуру знаний: если добавлена сущность, опиши её в разделе "Архитектура"; если изменена бизнес-логика, обнови раздел "Правила валидации". Документация всегда должна отражать "как код работает сейчас".

**Б. Планирование (Plan-Driven Development)**
Любое действие по разработке (фичи, рефакторинг) **обязано** начинаться с планарного артефакта, например, создания и обновления `PLAN.md` (или `.cursor/plans/`). Создай соответствующее правило или шаблон команды, обязывающее агента сначала разработать шаги, а потом писать код.

## Шаг 2.5. Реестр скилов (минималистичная модель)

Цель: агент **не выдумывает** скилы и не сканирует диск пользователя.

1. **Проектные скилы** (`.cursor/skills/<имя>/SKILL.md`): если в репозитории есть многошаговый сценарий, который повторяется 3+ раза и не покрывается базовыми командами — оформить как проектный скил. Добавить строку в первую таблицу `@.cursor/rules/project-skills-registry.mdc`.

2. **Глобальные скилы**: реестр **не строится сканированием диска**. Пользователь сам добавляет 2–5 скилов, релевантных текущему проекту, во вторую таблицу `project-skills-registry.mdc` (формат «сценарий → `/имя-скила`», без путей к файлам).

3. **Запрет**: агент не предлагает «давайте просканируем `~/.cursor/skills`» и не вписывает в таблицу скилы, существование которых не подтверждено пользователем или папкой `.cursor/skills/`.

4. **Merge при повторном bootstrap**: дополнить таблицы, не плодить второй файл с той же ролью.

5. В `CURSOR.md` (шаг 7) — одна строка-ссылка на `project-skills-registry.mdc` как источник истины. Никаких длинных списков скилов в `CURSOR.md`.

## Шаг 4. Hooks — генерация с нуля на основе анализа проекта

**Принцип** (см. `@.cursor/PRINCIPLES.md` P6): нет готовых примеров; хуки в чистом шаблоне отсутствуют и появляются только здесь, после реального анализа проекта. Формат — соответствующий Cursor IDE, кроссплатформенный (Node/`*.mjs` предпочтительнее `.sh`/`.ps1`, когда задача однотипна).

### 4.1. Анализ проекта — таблица решений

| Найдено в проекте | Полезный хук |
|-------------------|---------------|
| `PLAN.md` или `.cursor/plans/` | `plan-guard` на pre-commit: блокирует/предупреждает при коммите без активного плана. |
| `PROJECT_KNOWLEDGE.md` | `knowledge-sync` на post-edit: подсветить, что изменён код, но не док. |
| `.github/workflows/` или `.gitlab-ci.yml` | `ci-validate` на pre-push: запуск `node scripts/validate-layer.mjs` локально. |
| `.cursor/rules/*.mdc` (>3 файлов) | `rule-validator` на on-save: предупреждать о превышении лимитов из `LIMITS` валидатора. |
| `package.json` / `pyproject.toml` / `Gemfile` | Хуки под `lint` / `test` / `build` стека. |
| Отсутствие `PLAN.md` | **Не** генерировать `plan-guard` — иначе хук создаёт ложное трение. |

### 4.2. Правила генерации скриптов

- **Кроссплатформенность**: предпочитать Node.js (`.mjs`, без зависимостей) — работает на Windows/macOS/Linux без переписывания. Шелл-скрипты только когда стек проекта это уже требует.
- **Идемпотентность**: если нет git, нет нужного файла, нет нужной утилиты — скрипт молча выходит с кодом 0, **не** блокирует workflow.
- **Лимит «шумности»**: предупреждение — это `stderr` + exit 0; жёсткий блок (`exit 1`) только в безопасных pre-commit-сценариях вроде поиска секретов.
- **Документирование**: каждый скрипт начинается с заголовочного комментария «зачем он нужен» в 3–5 строк.

### 4.3. Конфигурация хуков

`hooks.json` (или эквивалент, ожидаемый Cursor IDE на момент bootstrap) генерируется минимально:

- `name`, `event`, `description`, `script`, `enabled`, опционально `globs`.
- Дата генерации фиксируется в самом файле.
- Все скрипты живут в `.cursor/hooks/` (или другом месте, явно согласованном).

### 4.4. Самоулучшение

Команда `/reflect` (`.cursor/commands/reflect.md`) после bootstrap уже опирается на git/валидатор/журнал, а не на воображаемую историю чатов. Хуки могут (опционально) дописывать короткие события в журнал внутри `PROJECT_KNOWLEDGE.md → AI Layer Health → Журнал рефлексий` — но это **не обязательно**: журнал может вестись и вручную при каждом `/reflect`.

### 4.5. Документация после генерации

- `PROJECT_KNOWLEDGE.md` → раздел «Архитектура → Hooks»: список, события, зачем.
- `CURSOR.md` → строка-ссылка на `hooks.json` (без копирования содержимого).
- `CHANGELOG.md` → запись «Added: hooks `plan-guard`, `knowledge-sync` (…)».

## Шаг 8. Финализация

1. **Дерево `.cursor/`** (кратко): правила, команды, hooks (если сгенерированы), plans, PRINCIPLES.md.
2. **`node scripts/validate-layer.mjs`** — обязательный зелёный прогон. Если красное — починить до завершения.
3. **`CHANGELOG.md`** — запись в раздел `[Unreleased]`: что добавлено / изменено / удалено и **почему именно этому проекту**.
4. **Реестр скилов** (`@.cursor/rules/project-skills-registry.mdc`): создан/обновлён; если глобальные скилы не подключаются — это явно зафиксировано пустыми таблицами.
5. **`/reflect`**: подтверждено, что команда есть и опирается на git + валидатор + журнал (не на «историю чатов»). Раздел «AI Layer Health» в `PROJECT_KNOWLEDGE.md` существует и описывает источники метрик.
6. **Token economy** применена: `.cursorignore` настроен, ссылки точечные, длинные тексты не дублируются в `CURSOR.md`.
7. **Дата + версия**: шапка `CURSOR.md` обновлена, версия в `CHANGELOG.md` согласована.

Предложи пользователю: «Через 5–10 задач запусти `/reflect`. Раз в неделю — `/audit`. Перед новым чатом — `/handoff`».

**Итог**: AI-слой — живая система, опирающаяся на реальные данные (git, валидатор, журнал), а не на декларации.

Начинай строго по порядку: **0 → 1 → 1.5 → 2 → 2.5 → 3 → 4 → 5 → 6 → 7 → 8**. Установку глобальных скилов не предлагай и не выполняй (см. справку выше).
