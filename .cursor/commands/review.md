# /review — Ревью дифа или изменений

Файл в `.cursor/commands/review.md` — текст, который подставляется в чат при выборе `/review`.

## Цель
Дать структурированное ревью изменений (ветка, PR или перечень файлов) с фокусом на риски, тестируемость и соответствие архитектуре из живой документации.

## Входы
- Что ревьюить: ссылка на PR, описание ветки или `@`-файлы/дифф.
- Критичность (обычная / высокая — безопасность, деньги, PII).

## Шаги для агента (обязательный порядок)

1. **Составить План** в `@PLAN.md` или `.cursor/plans/review-xxx.md`: объём ревью, гипотезы рисков, какие файлы прочитать.
2. **Собрать контекст**: `@PROJECT_KNOWLEDGE.md`, релевантные правила (`@.cursor/rules/architecture.mdc`, `@.cursor/rules/stack-specific.mdc` при наличии стека).
3. **Проанализировать диф**: корректность, граничные случаи, безопасность, производительность, читаемость, соответствие конвенциям репозитория.
4. **Выдать результат**: блок «ок», блок «замечания» с приоритетом (must / should / consider), блок «вопросы к автору».
5. **При высокой критичности**: по `@.cursor/rules/model-routing.mdc` предложи пользователю эскалацию на ярус C после краткого черновика на быстрой модели.
6. **Обновить Живую Документацию** только если ревью выявило расхождение «док vs код» — исправь док структурно, не логом.

## Ограничения
- Не переписывай код без явной просьбы пользователя (ревью ≠ рефакторинг).
- Не раздувай список nitpick: максимум 10–15 пунктов с приоритетами.

## Готово
- Есть список must-fix до мержа (или явное «блокеров нет»).
- При необходимости обновлён `@PROJECT_KNOWLEDGE.md`.
